# Database

PostgreSQL 16 with the extensions `vector` (pgvector), `pg_trgm`, `btree_gist`, `pgcrypto` and `citext`. The schema is owned by Alembic: never change tables by hand.

## Working with migrations

Run from `backend/` with the Compose database up:

```bash
uv run alembic upgrade head          # apply all migrations
uv run alembic downgrade base        # remove everything the migrations created
uv run alembic revision --autogenerate -m "describe the change"
uv run alembic check                 # fails when models and migrations differ
```

The connection comes from `DATABASE_URL`. Review every autogenerated revision before keeping it: autogenerate does not create extensions, enum types or sequences, and a migration must not import application models for enum values, because a revision has to describe the schema as it was when written.

Conventions used throughout:

- Primary keys are UUID version 4, generated by the database (`gen_random_uuid()`).
- All timestamps are `timestamptz`. The database stores UTC and the clinic time zone is applied in the service layer.
- All money columns are `numeric(12,2)`.
- Constraint and index names follow a fixed naming convention (see `app/db/base.py`) so downgrades and later migrations are deterministic.
- Enumerations are native PostgreSQL enum types. Each type is created and dropped explicitly in the revision that introduces it.
- Sensitive personal fields (`*_enc`) are `text` columns holding application-level ciphertext (`<key_id>:<base64url>`), written through `app/core/crypto.py`. See [security.md](security.md).

## Integrity rules enforced by the database

**Double booking.** Two exclusion constraints on `appointments` use a GiST index on `(dentist_id, slot)` and `(patient_id, slot)` with the range overlap operator, limited to rows whose status is `booked`, `confirmed`, `checked_in` or `completed`. Slots are half open (`[start, end)`), so back to back appointments are allowed. Cancelled and no-show appointments release the slot. The application maps the resulting error `23P01` to HTTP 409 in Phase 4.

**Slots** must be bounded and non empty.

**Invoices.** `total = subtotal - discount + tax`, the discount cannot exceed the subtotal, and invoice numbers come from `invoice_number_seq` starting at 1000. Only one non void invoice may exist per appointment, so a voided invoice can be replaced. Invoice items must satisfy `amount = round(qty * unit_price, 2)`. Payments must be positive.

**Schedules.** One weekly template row per dentist and weekday. Weekday uses ISO numbering from 0 (Monday). Breaks must come as a pair and lie inside working hours.

**Email.** `users.email` and `newsletter_subscribers.email` are `citext`, so uniqueness ignores case.

## Indexes

- `appointments (dentist_id, lower(slot))`, `appointments (patient_id)`, `payments (paid_at)`, `invoices (issued_at)`.
- Trigram GIN indexes on `patients.first_name` and `patients.last_name` for fuzzy patient search (`%` operator).
- HNSW indexes with `vector_cosine_ops` on `kb_chunks.embedding` and `intent_examples.embedding` (384 dimensions).

Row level security is not used. Patient scoping is enforced in the service layer and covered by tests.

## Default settings

Revision `0004` adds invoice discount reasons and void details, payment card last four digits, sandbox flag and recording user, item timestamps, constraints that keep invoice amounts and payer types consistent, the `ar_aging` and `ar_aging_summary` views and the `billing_tax_rate_percent` setting. Views are not tracked by Alembic autogenerate, so they live only in the migration.

Revision `0003` adds `appointments.late_cancel` and the `guest_verifications` table used for guest email codes.

Revision `0002` adds the authentication tables (`auth_tokens` for hashed one time email verification and password reset tokens, `mfa_recovery_codes` for hashed recovery codes), `users.email_verified_at`, `users.password_changed_at`, `patients.anonymized_at` and the retention settings `chat_retention_days` and `guest_anonymize_months`.

Revision `0001` seeds `app_settings` with booking rules (minimum notice, horizon, same day booking, buffer, slot grid), the cancellation window, the receptionist discount limit, reminder timing and the LLM failover threshold. Gemini rate limits are intentionally not seeded: they are read from Google AI Studio and entered by an administrator.

## Tests

`tests/db` runs against a real PostgreSQL server (default `127.0.0.1:5432`, override with `TEST_DATABASE_URL`). The tests create and drop their own databases, `meridian_schema_test` and `meridian_migration_test`, so development data is never touched. They are skipped when no server is reachable, unless `REQUIRE_DB=1` is set, as it is in CI.

Use `127.0.0.1` rather than `localhost` on Windows: resolving `localhost` first tries IPv6 and adds about a second to every connection.


Revision `0006` adds `kb_documents.embedded_hash`, `embedded_at` and `managed_by`, and makes `(intent, text)` unique in `intent_examples`.
